# 邮箱登录配置、迁移和部署操作手册

日期：2026-10-17。对应 [14 实施设计](14-邮箱登录与上云准备实施设计.md)、[16 自检记录](16-上云准备实现与自检记录.md)。当前有本地可测试实现和部署文件，尚无正式线上地址。外部认证项目、SMTP、域名、云服务器和异地仓库需配置后才能真实使用。

## 1. 现在先做什么

本地原用法仍是 `npm run dev` → `http://127.0.0.1:3000`，默认 `READWORDS_MODE=local`，只绑定本机，不要求登录。GitHub 存代码；SQLite 学习数据不会随 Git push 上传或自动同步。

建议先配置认证项目，在独立本地端口/测试库验证，再购买和配置部署资源。不要为了试登录直接修改正式本地库，不要把邮箱密码、令牌或备份发到聊天或提交 Git。

## 2. 配置邮箱＋密码（用户自己的认证后台操作）

1. 在 Supabase 创建用于此应用的认证项目，记录项目 URL 与 publishable key。应用只用 Auth，不使用其 PostgreSQL 存学习原文。不要配置 `service_role` 或 secret key。
2. 在 Auth 用户管理中预先创建你的邮箱账号并设置密码，确认邮箱验证完成；复制该用户 UUID。应用要求 UUID＋邮箱同时匹配。只改邮箱不能替代 UUID 配置；删除重建账号后 UUID 会变化，需要显式更新配置。
3. 关闭允许新用户注册、匿名登录及不使用的社交/手机登录。应用没有公开注册按钮或注册 API；提供方的公开注册也必须关闭。
4. 登录采用邮箱＋密码。密码长度/强度、会话时限及账号恢复策略在提供方后台设置；应用新密码表单限制 12–128 字符。认证 Cookie 为 HttpOnly，生产 Secure、SameSite=Lax、host-only，按 SDK 刷新，默认最多 7 天的浏览器 Cookie 周期；实际会话撤销/有效期还受提供方策略影响。
5. 配置 Site URL 和明确的 Redirect URLs。开发验证可用 `http://127.0.0.1:3001`；允许恢复页面 `http://127.0.0.1:3001/reset-password`。生产替换为唯一正式 HTTPS 域名，不加任意域名通配。
6. 修改 **Reset Password** 邮件模板，使链接指向本应用服务器校验入口。例如开发环境：

```html
<a href="http://127.0.0.1:3001/auth/confirm?token_hash={{ .TokenHash }}&amp;type=recovery">重置 ReadWords 密码</a>
```

生产改为 `https://你的正式域名/auth/confirm?...`。服务器向提供方验证一次性 recovery token_hash 后设置会话，并跳转固定 `/reset-password`；不接受外部 next/redirect 参数。链接失效或已使用时重新申请，不把 token_hash 发给他人。

7. 正式使用前配置自己的 SMTP，并真实验证收件、过期/重放、密码修改后的重新登录。提供方试用邮件限制不等于生产送达保证。应用找回接口统一返回“若该邮箱可用将收到邮件”；提供方发送失败只记固定运维错误代码，不暴露账号存在性。未收到邮件时检查 SMTP、模板、限额和后台日志。

参考：[官方密码登录/恢复指南](https://supabase.com/docs/guides/auth/passwords)、[邮件模板](https://supabase.com/docs/guides/auth/auth-email-templates)、[SMTP](https://supabase.com/docs/guides/auth/auth-smtp)。此文档不会替你创建账号、填写密码或开通付费资源。

## 3. 独立本地验证真实认证

在项目根目录新建 `.env.cloud-test`（Git 已忽略），填入自己的配置。以下为示例，不能照抄占位值运行：

```dotenv
READWORDS_MODE=cloud
READWORDS_ORIGIN=http://127.0.0.1:3001
READWORDS_DB_PATH=/absolute/path/to/isolated-test/readwords.sqlite
READWORDS_DIST_DIR=.next-cloud-e2e
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
READWORDS_OWNER_ID=真实认证用户UUID
READWORDS_OWNER_EMAIL=自己的邮箱
TZ=Asia/Shanghai
```

先结束本项目的 cloud E2E 测试服务，再在终端执行：

```bash
node --env-file=.env.cloud-test node_modules/next/dist/bin/next dev --webpack --hostname 127.0.0.1 --port 3001
```

保持终端运行，打开 `http://127.0.0.1:3001`。验证未登录无法访问业务数据，只有指定账号可登录，退出后失去访问权限；完整测试“忘记密码→真实邮件→新密码→重新登录”。已有 3000 本地服务和正式学习库不因此迁移。HTTP 回环仅允许非 production 的开发验证；生产 cloud 只接受 HTTPS 配置。

`.env.cloud-test` 与 `.next-cloud-e2e` 输出目录不供两套服务并行使用。不要把此临时验证当成正式上云，也不要把生产认证密钥写成 NEXT_PUBLIC 环境变量。

## 4. 数据冻结、一致性备份和核对

`npm run ops -- ...` 使用 Node 24 内置 SQLite，不初始化应用 Store，不清理复习租约。路径均替换为实际文件。下例用于你自己的受控迁移操作：

```bash
npm run ops -- maintenance /absolute/path/readwords.sqlite on
npm run ops -- manifest /absolute/path/readwords.sqlite
npm run ops -- backup /absolute/path/readwords.sqlite /absolute/path/migration-backups
npm run ops -- compare /absolute/path/readwords.sqlite /absolute/path/migration-backups/实际快照文件.sqlite
```

维护 on 会等待在途写事务结束，再阻止所有业务写入；查询和 JSON 导出继续允许，复习读取不推进租约/卡片状态。浏览器得到明确维护提示。若同时设置 `READWORDS_READ_ONLY=1`，仅切换数据库维护开关不能解除这个环境变量开关。

迁移清单比较 schema、八张业务表计数/ID/完整字段摘要与 generation；运行租约、维护开关不参与业务相等。相同数量但不同释义/ID 会核对失败。必须保留 archived/deleted/ignored/saved 状态、导入元数据及全部复习历史，不能靠重传 Excel 迁移。

原生 `.sqlite` 快照通过 SQLite Backup API 生成，无需生拷运行中的 WAL 主文件；只有完整性和外键校验通过、fsync 后才发布目标文件。不要在网页 JSON 恢复入口上传原生 SQLite。

SQLite 迁移时先核对 **尚未被目标应用启动修改运行状态** 的副本；启动后运行会话可能正常归一为 paused/version 更新，因此不要将这类已知运行恢复变化误称为迁移丢数据。JSON 恢复会更新 generation，不能用“generation 必须相同”的原生迁移 compare 检查 JSON 替换结果。

## 5. 生产部署配置

目标：一台服务器、一个应用实例、同机持久卷 SQLite、Caddy HTTPS、独立加密备份仓库。部署文件在 `deploy/`；当前开发环境没有 Docker，以下命令尚未在真实容器和线上执行。

准备 Docker Engine/Compose、正式域名指向服务器、80/443 入口。创建项目根目录 `.env.cloud`（Git 忽略），按 `.env.example` 填：域名、Supabase 项目/所有者、restic 异地仓库及其凭据。不要将完整 `docker compose config` 输出公开，它可能含凭据；检查配置用 `config --quiet`。

`RESTIC_PASSWORD_FILE` 为仓库之外、受限权限的主机绝对路径；备份容器以 UID 1000 运行，必须能读取该文件。备份仓库要与应用服务器处于独立故障域，不能只写同一云主机的另一目录。妥善保留 restic 密码与仓库访问恢复方式；丢失密码无法解密备份。

```bash
docker compose --env-file .env.cloud -f deploy/compose.yaml config --quiet
docker compose --env-file .env.cloud -f deploy/compose.yaml build app
docker compose --env-file .env.cloud -f deploy/compose.yaml run --rm --entrypoint restic backup init
```

`restic init` 只对新仓库执行；已有仓库使用 `snapshots`/`check` 验证，不重复初始化。备份容器与应用使用同一已构建镜像。首次空库部署可启动 `up -d`；迁移正式库则先按下一节放入冻结快照，不能先开放一个空库写入再覆盖。

```bash
docker compose --env-file .env.cloud -f deploy/compose.yaml up -d
docker compose --env-file .env.cloud -f deploy/compose.yaml ps
```

应用端口不发布到公网，Caddy 将正确 Host 转交应用并按端点限制 body；应用仅相信显式 origin，不从任意转发头决定可信域名。认证使用服务端 Cookie。Docker 镜像默认 cloud，未配置不得匿名启动。健康接口只返回 ok 状态，不输出路径/数据/配置；应用健康就绪后才启动代理与备份。

## 6. 放入冻结数据与正式切换

1. 本地维护 on，等待写入结束，生成并核对一致性原生快照，保存源库路径、提交和清单。让所有设备保存未保存输入。
2. 经受控 SSH/SCP 把快照送至服务器仓库之外的私有临时目录。在空 named volume 里安装冻结快照：

```bash
docker compose --env-file .env.cloud -f deploy/compose.yaml run --rm --no-deps --user root --entrypoint sh -v /absolute/server/transfer:/transfer:ro app -c 'install -m 600 -o 1000 -g 1000 /transfer/frozen.sqlite /app/data/readwords.sqlite'
```

此命令仅用于确认为空的目标数据卷。目标已有数据时先停止全部应用/备份进程并保全当前一致性快照，按回退流程处理，不用该命令直接覆盖运行库或遗留 WAL/SHM。

3. 在目标应用尚未启动前运行 `node scripts/ops.mts manifest /app/data/readwords.sqlite` 导出目标清单，与源清单逐项比对；主机本地的 compare 工具也可用于比较下载的两个冻结文件。所有核对完成后才启动目标应用，冻结快照中的维护开关仍为 on。
4. 登录目标网址验证只读内容及复习数据，再执行：

```bash
docker compose --env-file .env.cloud -f deploy/compose.yaml exec app node scripts/ops.mts maintenance /app/data/readwords.sqlite off
```

5. 云端开始日常写入后，本地原库仍保持维护 on，只作回退副本，不同时维护两份日常写入库。Mac 关机后验证手机/iPad 仍能查阅；检查登录、搜索、P1、详情、Mac 导入/维护、断网与冲突。未完成实际设备验收不能称 C1 上线。

## 7. 自动备份、故障与恢复

备份容器就绪后立即运行一次，之后每隔 86400 秒执行。每次先生成经过校验的 SQLite 快照，再用 restic 加密上传、按标签/主机保留 7 个日备份和 4 个周备份、prune/check，成功后才清理本地过期快照并写 `.last-success`。作业失败退出非零并输出固定错误码，调度继续下一周期；超过 26 小时无成功记录时容器 unhealthy。应将该状态和 `READWORDS_BACKUP_FAILED` 接入部署环境告警，当前未接通真实通知渠道。

```bash
docker compose --env-file .env.cloud -f deploy/compose.yaml logs --tail 100 backup
docker compose --env-file .env.cloud -f deploy/compose.yaml run --rm --entrypoint node backup scripts/backup-job.mts
docker compose --env-file .env.cloud -f deploy/compose.yaml run --rm --entrypoint restic backup snapshots
```

单次手动作业可能遇到已有调度作业锁，此时应等待，不并发运行。异常退出遗留 `.backup.lock` 时先停止备份服务并确认没有作业，再清理锁后重新运行；不要在备份活动时删除锁。`.partial` 不可用作恢复。

每月至少一次恢复到隔离目录：`restic restore <snapshot-id> --target <隔离目录>`，从恢复的 `/app/backups/` 下选对应 SQLite 文件，用 manifest/integrity/外键检查，使用兼容版本在隔离端口打开并核对业务；恢复后的旧租约在新服务进程启动时失效，未结束会话暂停。不要为演练覆盖正式卷。完整异地恢复命令须在安装 restic 的受控主机或显式挂载隔离恢复目录的临时容器执行。

云端未写入时可停云端、恢复原本地冻结库；云端已有新写入则先冻结云端并备份最新库，核对后恢复兼容本地实例，不能直接用旧本地库覆盖。所有恢复均先停止相关服务并保全现状；原生数据库的 WAL/SHM 不可在运行中手动删除。

## 8. 更新与验收

更新前维护只读并完成备份，构建新镜像、保留数据卷后重启应用，核对并解除维护。不要执行会删除 named volumes 的 `down -v`。有 schema 变化时先按兼容迁移设计验收，不能盲目回退旧程序读取新库。

当前自动化结果和剩余缺口以 16 为准。真实认证/邮件、Docker/Caddy、restic 加密异地恢复、服务器重启/升级保数据、域名 HTTPS、手机/iPad、通知与费用预算均需实测；部署文件存在不等于这些项目已通过。
